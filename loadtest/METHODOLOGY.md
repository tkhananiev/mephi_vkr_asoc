# Методика нагрузочного сравнения ASOC и Defect Dojo

Фиксированные решения (чтобы не спорить в процессе):

| Решение | Выбор |
|--------|--------|
| Генератор нагрузки | **wrk** |
| Откуда гоняем | **рабочая станция** (или один и тот же внешний хост для обоих продуктов) |
| Доступ к ASOC для «честного» сравнения приложений | **не через публичный Ingress** — `kubectl port-forward` на **`api-service:8080`** и/или **`processing-service:8082`**, wrk бьёт в **`http://127.0.0.1:...`**. Так мы не измеряем лимит **ingress-nginx**. |
| Доступ к Defect Dojo | **тот же класс**: прямой порт на хосте, где крутится DD (например `http://127.0.0.1:8080/login`), **без** лишнего reverse-proxy, если он не часть эталонного стенда. Если DD только за nginx — грузим оба продукта за аналогом (и фиксируем в отчёте). |
| Сопоставимость | Одинаковые **`-t`**, ступени **`-c`**, **`-d`** на этапе сравнения (см. скрипт `run-series.sh`). |
| Наблюдение ASOC | **Grafana** (`deploy/k8s/monitoring`): дашборд ASOC — CPU подов, **HPA текущие реплики**; скрины во время ступеней **`-c`**. |
| Критерий деградации | Любой из: p99 \> 2× от базового, \>1% ошибок/не-2xx в wrk, массовые таймауты, OOM/CrashLoop подов приложения. |
| НФТ по масштабированию (ASOC) | HPA целится в **90% CPU** от `requests` — `deploy/k8s/hpa.yaml`. |

### Сопоставление с твоими предварительными замерами (wrk → localhost)

Раньше ты гонял **`wrk`** на **`http://localhost:8080/api/users`**, ступени в духе:

- **средняя:** `-t8 -c200 -d15s`
- **повышенная:** `-t12 -c800 -d20s`
- **экстремальная:** `-t16 -c1500 -d20s`

и интерпретировал рост средней латентности при «плато» throughput как **точку насыщения** — это хорошо стыкуется с нашим критерием деградации и с выводом про устойчивую архитектуру.

**В ASOC** эндпоинт **`/api/users`** может быть не у `api-service` (актуальные маршруты см. в сервисах); для **сопоставимой по смыслу «лёгкой» HTTP-нагрузки** через тот же **`kubectl port-forward`** на **api-service:8080** используй например **`GET /health`**. Для сценария **с работой БД** — отдельный проброс **`processing-service:8082`** и **`GET /api/v1/groups?limit=…`** (RPS будет **ниже**, чем на «пустом» health — это нормально; для сравнения с Defect Dojo важно выбрать **соразмерный по тяжести** URL на обеих сторонах).

**Три твоих уровня без скрипта** (подставь нужный путь):

```bash
kubectl port-forward -n asoc svc/api-service 8080:8080   # отдельный терминал

wrk -t8  -c200  -d15s --latency http://127.0.0.1:8080/health
wrk -t12 -c800  -d20s --latency http://127.0.0.1:8080/health
wrk -t16 -c1500 -d20s --latency http://127.0.0.1:8080/health
```

В `run-series.sh` по умолчанию **один** `THREADS` на все ступени **`-c`**; если нужна полная копия схемы «разные t на уровне», либо три отдельные команды как выше, либо три прогона с разными `THREADS` и коротким `RAMP_CS`.

## Сценарии по командам (копипаст)

Предполагается: **kubectl** смотрит на нужный кластер, namespace **`asoc`** развёрнут, **wrk** установлен на этой же машине.

### A — ASOC, лёгкий HTTP (`api-service`, без Ingress)

**Терминал 1** (оставить открытым, пока идёт тест):

```bash
kubectl port-forward -n asoc svc/api-service 8080:8080
```

**Терминал 2** — три уровня нагрузки (как в твоих предварительных замерах), лог вручную или в файл:

```bash
wrk -t8  -c200  -d15s --latency http://127.0.0.1:8080/health  | tee wrk-asoc-l1.txt
wrk -t12 -c800  -d20s --latency http://127.0.0.1:8080/health  | tee wrk-asoc-l2.txt
wrk -t16 -c1500 -d20s --latency http://127.0.0.1:8080/health  | tee wrk-asoc-l3.txt
```

Параллельно открой **Grafana** и сделай скрины дашборда ASOC на уровнях L2–L3 (CPU / HPA).

---

### B — ASOC, нагрузка с обращением к БД (`processing-service`)

**Терминал 1:**

```bash
kubectl port-forward -n asoc svc/processing-service 8082:8082
```

**Терминал 2** (те же или согласованные `-t/-c/-d`):

```bash
wrk -t8  -c200  -d15s --latency 'http://127.0.0.1:8082/api/v1/groups?limit=50'
wrk -t12 -c800  -d20s --latency 'http://127.0.0.1:8082/api/v1/groups?limit=50'
wrk -t16 -c1500 -d20s --latency 'http://127.0.0.1:8082/api/v1/groups?limit=50'
```

(Кавычки из-за `?` в URL.)

---

### C — ступенчатый рост только по `-c` (один `THREADS`, логи в `loadtest/results/`)

**Терминал 1:**

```bash
kubectl port-forward -n asoc svc/api-service 8080:8080
```

**Терминал 2:**

```bash
cd mephi_vkr_asoc/loadtest

export TARGET_URL='http://127.0.0.1:8080/health'
export THREADS=8
export DURATION_PER_STEP=30s
export RAMP_CS='50 100 200 400 600 800 1000'

./run-series.sh
```

Смотри вывод: каталог **`loadtest/results/<дата-время>/`** с `wrk-c*.txt` и `summary.txt`.

---

### D — Defect Dojo (после остановки ASOC или на другой машине)

Подними DD по **`defectdojo/README.md`**, подставь свой порт вместо **8081**:

**Терминал 2** — те же команды, что в **A**, но URL DD:

```bash
wrk -t8  -c200  -d15s --latency http://127.0.0.1:8081/login
wrk -t12 -c800  -d20s --latency http://127.0.0.1:8081/login
wrk -t16 -c1500 -d20s --latency http://127.0.0.1:8081/login
```

Или **те же** переменные, что в **C**, и `./run-series.sh` с `TARGET_URL=http://127.0.0.1:8081/login`.

---

### E — проверка контекста кластера (если несколько kubeconfig)

```bash
kubectl config current-context
kubectl get pods -n asoc
kubectl get hpa -n asoc
```

## Порядок работ

### Фаза 0 — подготовка

1. Кластер: ASOC, **metrics-server**, **HPA**, **Prometheus/Grafana** (см. `deploy/k8s/monitoring/README.md`).
2. Установить **wrk** на машине, с которой будет нагрузка.
3. Создать каталог результатов не обязательно — скрипт сам положит логи в `loadtest/results/<timestamp>/`.

### Фаза 1 — ASOC

1. Терминал A: проброс **API** (основной сценарий для сравнения «лёгкий HTTP»):

   ```bash
   kubectl port-forward -n asoc svc/api-service 8080:8080
   ```

2. Опционально второй проброс для сценария с БД: `processing-service:8082`.

3. Терминал B — ступенчатый прогон (пример, параметры задать самим единожды и использовать те же в фазе 2):

   ```bash
   cd mephi_vkr_asoc/loadtest
   export TARGET_URL='http://127.0.0.1:8080/health'
   export THREADS=8
   export DURATION_PER_STEP=30s
   export RAMP_CS='50 100 200 400 600 800 1000'
   ./run-series.sh
   ```

4. Параллельно **Grafana**: снять скрины при 1–2 ступенях, где виден рост CPU и/или реплик HPA.

5. Зафиксировать **первую ступень деградации** (или максимальную устойчивую) по критерию выше.

### Фаза 2 — Defect Dojo

1. Остановить ASOC (масштаб в 0 или не поднимать), поднять **только** Defect Dojo — см. `defectdojo/README.md`.
2. Тот же `TARGET_URL` по смыслу нагрузки (например `http://127.0.0.1:<порт>/login`).
3. **Те же** `THREADS`, `DURATION_PER_STEP`, **`RAMP_CS`** (обязательно для сравнения строк в таблице отчёта).

   ```bash
   export TARGET_URL='http://127.0.0.1:<DD_PORT>/login'
   ./run-series.sh
   ```

### Фаза 3 — отчёт

Заполнить **`LOAD_TEST_REPORT.md`**: таблица сравнения, выводы. Прикрепить архив каталогов `loadtest/results/...` и скрины Grafana (только для ASOC; для DD — аналог по метрикам, если поднимали мониторинг).

---

## Что сознательно не делаем

- Не наращиваем `-c` до явного исчерпания **Ingress**, если цель — сравнить приложения (для ASOC используем port-forward).
- Не смешиваем в одной строке таблицы «ASOC через port-forward» и «DD через CDN» — тип доступа должен быть согласован и описан.

Правки только по согласованию; базовая версия зафиксирована в репозитории рядом с `run-series.sh`.
